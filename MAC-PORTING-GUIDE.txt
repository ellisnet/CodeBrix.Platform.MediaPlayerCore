A handoff document for the AI coding agent working on Jeremy's Mac

WHAT ALREADY WORKS ON macOS (do not rebuild these)
--------------------------------------------------
The capture pipeline itself is platform-neutral through libvlc:
  - WebcamSession preview (vmem frame sink), CapturePhoto, overlay compositing,
    MP4/H.264 recording (direct sout AND the imem frame-path), and the sidecar
    WAV recorder all run through CodeBrix.MediaCore and need NO macOS-specific
    code. The session already builds an "avcapture://<device-id>" MRL on macOS
    (see Internal/CaptureMediaFactory.cs) — libvlc's avcapture module does the
    actual capture.
  - VideoFrameSource.IsSupported probes the imem plugin at runtime; on a Mac
    libvlc install (VLC.app or VideoLAN.LibVLC.Mac) verify it returns true.

WHAT IS MISSING ON macOS
------------------------
1. DEVICE ENUMERATION — the flagship feature. The stub at
   src/CodeBrix.Webcam/Internal/Darwin/DarwinDeviceProvider.cs throws
   PlatformNotSupportedException pointing here. Replace it with a real
   implementation that returns fully populated ImagingMediaDevice objects
   (see Internal/ImagingMediaDevice.cs — the shared POCO all providers use).

   AVFoundation is the API:
     - Device list: AVCaptureDevice.DiscoverySession with device types
       (AVCaptureDeviceTypeBuiltInWideAngleCamera, AVCaptureDeviceTypeExternal /
       ...ExternalUnknown on older SDKs) for AVMediaTypeVideo.
     - Identity: uniqueID (stable — use as IImagingMediaDevice.Id; it is also
       what libvlc's avcapture MRL accepts), localizedName (FriendlyName),
       modelID + transportType for hardware info. USB VID/PID: parse the
       modelID string (e.g. "UVC Camera VendorID_1133 ProductID_2140") or use
       IOKit lookup — best effort, 0 when unknown.
     - Capability matrix: device.formats → each AVCaptureDeviceFormat exposes
       formatDescription (CMVideoFormatDescriptionGetDimensions → width/height,
       CMFormatDescriptionGetMediaSubType → fourcc) and
       videoSupportedFrameRateRanges (min/max fps per format). Map to
       ImagingMediaCapability; when min != max, set isFrameRateRange = true
       with the two endpoints (the same convention the Windows provider uses).
     - Controls: macOS exposes FAR less than V4L2/DirectShow. Realistic v1:
       focus mode (locked/auto/continuous), exposure mode, white-balance mode
       via AVCaptureDevice lock-for-configuration — model them as Boolean/Menu
       IImagingDeviceControl entries with SupportsAuto. UVC extension-unit
       controls (brightness/contrast/...) are NOT reachable through
       AVFoundation; skipping them is acceptable and documented behavior.
       An empty controls list is legal — do not fabricate ranges.
     - Microphone pairing: AVCaptureDevice.linkedDevices on the video device
       (or DiscoverySession over AVMediaTypeAudio matching by localizedName)
       → ImagingAudioPairing. The DeviceId should be whatever the audio MRL
       needs (see item 2).

2. AUDIO CAPTURE MRLs. Internal/CaptureMediaFactory.cs and
   Internal/AudioSidecarRecorder.cs currently build alsa:// (Linux) and
   dshow:// (Windows) audio inputs. macOS needs the avaudiocapture (or
   qtsound, depending on the libvlc build) input added to both switch points,
   with whatever device identifier that module accepts. Grep for
   "IsWindows()" in those two files to find the exact spots.

3. INTEROP MECHANISM — your choice, two workable routes:
   a) Direct Objective-C runtime P/Invoke (objc_msgSend against
      libobjc.A.dylib + CoreMedia/AVFoundation frameworks). Zero native build
      steps, but objc_msgSend marshaling for struct returns
      (CMVideoDimensions etc.) is fiddly on arm64.
   b) A tiny native shim dylib (a few C functions wrapping the AVFoundation
      calls, returning plain C structs/strings), compiled on the Mac and
      packed into the nuget under runtimes/osx-arm64/native (add osx-x64 if
      Intel support matters). Jeremy has explicitly approved the nuget being
      BUILT ON THE MAC to embed native bits, so this route is fully
      sanctioned — and probably the saner one.

RULES THAT BIND THIS WORK (same as the rest of the repo)
--------------------------------------------------------
  - Read AGENT-README.txt in full first. NRT stays OFF (no `?` on reference
    types), file-scoped namespaces, XML doc comments on all public members,
    no <NoWarn>.
  - THE NO-LEAK RULE: nothing public in CodeBrix.Webcam may expose a
    CodeBrix.Platform.MediaPlayerCore.* type. PublicApiLeakTests enforces it.
  - Keep the public API EXACTLY as-is; this is an internal-provider fill-in.
    Wire the provider into WebcamDevices.cs (replace the Darwin branch).
  - All packages version together on the 3.x.y.z scheme; nothing ships
    out-of-band.
  - Tests: add Mac-relevant tests to tests/CodeBrix.Webcam.Tests; the live
    ones gate on CODEBRIX_WEBCAM_RUN_CAMERA_TESTS=1 like LiveCameraTests.cs.
